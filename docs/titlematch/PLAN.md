# Vetro Title Identity — план v2

Дата: 2026-10-27. Ветка: `feat/title-identity-foundation`.
Текущий этап: исследование, воспроизводимая загрузка ресурсов и аудит данных.
Модель Vetro ещё не обучена; размеры, задержки и метрики ниже — критерии допуска.

## Что строим

Общий локальный механизм идентификации для пяти типов коллекции: аниме, манга,
фильмы, сериалы и аудиокниги. Первый обучающий корпус — аниме; остальные типы
подключаются по мере появления проверенных данных и отдельных оценок качества.
Успех на аниме не разрешает автоматически включать модель для книг или кино.

Система состоит из независимых частей:

1. `TitleIdentityResolver`: типизированные внешние ID, подтверждённые соответствия,
   конфликты и словарь псевдонимов.
2. `TitleCandidateIndex`: поиск кандидатов по ID, полным названиям, префиксам,
   символьным n-граммам и вариантам транслитерации.
3. `TitlePairScorer`: оценка оставшихся пар с учётом метаданных.
4. Политики конкретных сценариев: рекомендации, поиск, обогащение, импорт.
5. Отдельный граф отношений франшизы. Он не является словарём идентичности.

Сходство названий и семантическая близость сами по себе не доказывают идентичность.
Сеть не должна угадывать неизвестные переводы без словаря. Сначала проверяем,
сколько реальных проблем решает один словарь с надёжными ID.

## Единицы идентичности

`CatalogEntity` — запись определённого типа и уровня: произведение/фильм,
сериал, сезон, эпизод, литературное произведение, издание или запись озвучки.
`FranchiseRelation` хранит продолжение, ремейк, адаптацию и прочие отношения
между разными сущностями. Не объединяем сезон с сериалом, мангу с аниме,
экранизацию с книгой, разные озвучки одной книги с одной записью прослушивания.

ID имеет ключ `(provider, mediaKind, entityLevel, value)`. Например,
`tmdb/movie/550` и `tmdb/tv/550` различны. MAL anime/manga также различны.
Shikimori и MAL учитываем с происхождением: зависимые источники не дают двух
независимых подтверждений. Один ID сериала может покрывать несколько записей
аниме; маппинг сезона/эпизодов не превращаем в equivalence edge.

Результат: `SAME_ENTITY | DIFFERENT_ENTITY | UNCERTAIN`, причины,
конфликты, источники доказательств, версии индекса/модели/политики и при наличии
калиброванная вероятность. `DIFFERENT_ENTITY` требует доказательств различия;
отсутствие общего ID — `UNCERTAIN`. Противоречивые ID — карантин/неопределённость
с запретом автоматического действия, пока конфликт не разрешён. Подтверждённое
различие типа/сезона — `DIFFERENT_ENTITY`. Разница годов обычно мягкий признак,
а не безусловный запрет: известны локальные даты премьер.

Нормализация хранит исходную строку и несколько поисковых представлений.
Unicode NFKC/case folding, пунктуация, ё/е и транслитерация — отдельные версии.
Числа, римские номера, часть/сезон, OVA, special, remake не выбрасываются из
признаков идентичности. Совпадающий нормализованный псевдоним может принадлежать
нескольким сущностям и возвращает множество кандидатов.

## Поведение по сценариям

| Сценарий | Использование | Действие при неопределённости |
|---|---|---|
| Рекомендации | Сначала ID/словарь, затем оценка ограниченного списка пар. Отдельно правила франшизы и свайпов | Сохранить рекомендацию; модель сначала только в shadow mode |
| Поиск | Prefix/n-gram retrieval → top-K rerank; точные ID выше текстового сходства; тип, год и язык помогают рангу | Показать разные варианты; не скрывать сезон/ремейк; короткий запрос не считать полным названием |
| Обогащение | Найти ту же сущность у поставщика; проверить кандидатов и разрыв top-1/top-2 | Не записывать сомнительные ID/поля; предложить выбор кандидата |
| Импорт / кнопка «добавлено» | Объяснимый сигнал возможного дубликата в соответствующем типе | Разрешить добавление или ручной выбор |
| Удаление / merge / sync | Только отдельные детерминированные правила и пользовательское действие | Вероятностный результат не разрешает удаление/слияние |
| Подбор источника воспроизведения | В перспективе повторное использование доказательств с проверкой сезона/эпизода/озвучки | Сохраняются действующие строгие правила воспроизведения |

## Фактические точки интеграции

- `domain/recommendations/RecommendationFilter.kt`: точные нормализованные
  названия, ID и свайпы. `CandidateMerger` и `LibraryTmdbIdBackfill` также
  требуют согласованных правил. Нормализованные названия сейчас нельзя считать
  глобальным ключом без типа и коллизий. Новое правило франшиз из исходной
  незакоммиченной рабочей папки требует отдельной последующей сверки.
- `domain/enrichment/TitleCandidateSearch.kt`: уже собирает кандидатов из
  источников и ранжирует их; это вход для candidate reranking.
- `core/network/.../ids/TitleIdResolver.kt`: уже объединяет ID и источники;
  расширение через `TitleIdContributor` / `VETRO-TAIL[title-id-source]`.
  `TitleInfoEnricher` записывает результат: именно перед записью нужен gate.
- `domain/search/AddFromApiUseCase.kt`, `DuplicateTitleRule.kt`: сохранение и
  удаляющее схлопывание — отдельная граница, ML сюда не подключаем автоматически.
- `sync/TitleMatcher.kt`, `MovieTitleMatcher.kt` и
  `media/source/movieseries/MediaIdentityMatcher.kt`: существующие разные
  правила; не заменяем одним порогом. Последний уже различает conflict/no evidence.
- `domain/TitleNormalization.kt`: общая текущая нормализация удаляет разделители;
  новую версию вводим рядом, с паритетными тестами и явной миграцией ключей.

## Данные и происхождение

Сырые ресурсы лежат в `tools/titlematch/.cache/` вне Git и APK. В Git — lock,
код загрузки, результаты аудита и этот план. Каждый файл имеет URL, фиксированный
релиз/commit, SHA-256, размер, время проверки, назначение и статус использования.
Для новой загрузки отчёт фиксирует downloaded_at; для ранее сохранённого файла —
время проверки и его файловую дату, не выдавая её за подтверждённое время загрузки.
Загрузка для исследования не означает разрешение обучения или распространения.

1. Manami `2026-27`: исторический baseline, зафиксировать LICENSE/README,
   проверить реальное количество записей/псевдонимов и коллизии ID.
2. cedya `2026-43`: отдельный snapshot; отчёт diff по устойчивым ID, исчезнувшим
   записям, split/merge и конфликтам. Не заменять и не сливать корпуса вслепую.
3. Fribb: только исследовательский карантин до проверки разрешения использования;
   сохранить сезонность, episode offset и one-to-many. Не импортировать
   франшизные кластеры как идентичность.
4. Wikidata: CC0 labels/aliases и типизированные ID из ограниченных запросов или
   целевых сущностей. Начать с маленькой выборки всех пяти доменов; затем
   выгружать страницами, кэшировать, соблюдать backoff и идентифицирующий User-Agent.
   Русские названия — из ru labels/aliases, без автоматического перевода.
5. Shikimori/Jikan/TMDB и прочие поставщики: сначала условия и происхождение;
   массовую выгрузку не включать до обоснованного разрешения. Лицензия клиентской
   библиотеки не является лицензией данных. AniList API для нового корпуса
   не опрашивать; унаследованные данные также требуют проверки происхождения.

Схема: `entities.parquet`, `aliases.parquet`, `external_ids.parquet`,
`relations.parquet`, `evidence.parquet`, `quarantine.parquet`.
В aliases: entity_id, original_text, search_keys, language/script (unknown допустим),
alias_kind, provider, revision, license_class, evidence_id.
В entities: стабильный internal_id, media_kind, entity_level, format, даты,
автор/создатель при наличии, completeness. Изменение состава ID не меняет internal_id.
Ни год, ни язык, ни число эпизодов не заполняются выдуманным значением.

## Пары и обучение

Положительные пары — только проверенная одна сущность. Synthetic typo даёт
дополнительный признак устойчивости, но не доказательство нового перевода.
Перестановки/транслитерации генерируем осторожно; цифры сезонов не модифицируем.
Близкие отрицательные пары извлекаем из реального candidate retrieval: соседние
сезоны, ремейки, одноимённые фильмы, манга/аниме, книги разных авторов, OVA.
Не считаем любую пару без общего ID отрицательной. Неполную связь отправляем в
unlabeled/quarantine. Источниковое дублирование не увеличивает вес пары.

Разбиение сначала по группам произведений/франшиз/адаптаций/коллизий названий,
потом генерация пар, индексов, аугментаций и hard-negative mining внутри split.
80/10/10 — ориентир по размеру групп; giant components и перекосы публикуем.
Не допускаем одно и то же произведение по разным ID в разных split.
Отдельные оценки: unseen entities/franchises (обобщение модели), полный словарь
известных сущностей (реальная resolver-задача), temporal holdout и русские
ручные сценарии. Test не участвует в выборе порога, mining или калибровке.

Кандидаты сравниваются на одинаковых split и retrieval:

1. Текущие правила и затем ID+словарь без ML — обязательные baselines.
2. RapidFuzz/символьные n-граммы + компактный LightGBM: Jaro/Levenshtein,
   token overlap, числа/сезоны, язык, тип/год, полнота и источники. Без признака
   «конкретный entity_id» и без включения ID-доказательств в чистую title-метрику.
3. Siamese CharCNN с общим энкодером и симметричной головой
   `[abs(a-b), a*b, metadata]`. Unicode/byte представление выбрать экспериментом;
   фиксировать длину, truncation policy, unknown coverage, vocab hash, seed.
   Цель ≤1.5 MB INT8, без обещания до экспорта. Учить с нуля: готовых весов Vetro нет.
4. Potion 2M — скачиваемый английский контроль; multilingual MiniLM INT8 —
   тяжёлый офлайн-контроль retrieval/возможный teacher, не Android dependency.
   Сходство teacher не становится автоматической разметкой SAME_ENTITY.

Решение о победителе — по false positives, coverage и общей стоимости. Если
словарь или LightGBM достигают целей, CharCNN не становится обязательным.
Ранжирование поиска обучается/калибруется на query→entity сессиях отдельно от
полных title→title пар; префиксы, опечатки, аббревиатуры и top-2 ambiguity входят
в контрольный набор. Сеть идентичности не заменяет рекомендательную модель вкуса.

## Проверка и критерии выпуска

| Область | Предварительный gate |
|---|---|
| Автоматический отсев рекомендаций | precision ≥99.9%, нижняя односторонняя 95% граница ≥99.9% на репрезентативных срабатываниях; измерять coverage и baseline |
| Recall идентичности | +10 п.п. к старому правилу при том же precision; если baseline у потолка — отдельно согласовать достижимую цель |
| Сезоны/ремейки/адаптации | 0 ошибок в зафиксированном challenge set; размер и состав набора публикуются |
| Обогащение | тот же строгий precision gate на автоматически принятых кандидатах; доля abstain и загрязнение полей публикуются |
| Поиск | Recall@50 кандидатов ≥99% на покрываемых сущностях; MRR/NDCG@10 и Recall@10 не хуже baseline, отдельно RU/EN/JA и домены |
| Модель | ≤1.5 MB для мобильного кандидата; оценить post-quantization regression |
| Android | warm p95 ≤10 ms/пару на названном среднем CPU, отдельно cold start, RAM, cancellation и пакет 20 рекомендаций |
| Размер | замерить APK/AAB diff, ABI/runtime, полный/доменные словари и download pack; бюджет индекса определить после аудита |

Для нуля ошибок требуется как минимум 2,995 независимых репрезентативных
принятых совпадений для указанной односторонней границы. Пары одной франшизы
зависимы: считать также confidence interval/bootstrap по группам; одних
синтетических пар недостаточно. Публикуем n, FP, FN, prevalence, precision-recall,
ECE/reliability curves и результаты отдельно по языкам/типам/длинам/известным ID.
Числа не являются уже достигнутыми результатами.

## Android и безопасное внедрение

Индекс SQLite/FTS + таблицы n-грамм строится офлайн; не сравниваем каждый
результат с полной библиотекой. Оценка top-K, LRU-кэш на версии и batch inference.
FTS Unicode/tokenization и фактическую версию SQLite проверяем на minSdk.
Обновление индекса: manifest, checksum, schema compatibility, атомарная замена,
rollback и сохранение старой версии при повреждении/отсутствии сети. Никаких
автоматических скачиваний моделей на устройстве на этом этапе.

Для CharCNN сначала минимальный export spike PyTorch→LiteRT, затем обучение.
LiteRT версию и путь экспорта фиксируем по результату spike: совместимость
операторов, настоящая INT8 calibration на train subset, int8 I/O, паритет Python/
Kotlin preprocessing, отсутствие незаявленного float fallback. PyTorch INT8 сам
по себе не означает готовый TFLite. Для LightGBM оцениваем компактный evaluator
по реально используемым операциям и golden vectors, не тащим Python в Android.

Rollout: replay → локальный shadow с причинами расхождений → ручная проверка →
опциональное включение рекомендаций → поиск → обогащение. У каждого потребителя
свой флаг/порог и мгновенное возвращение к старым правилам. Журналы локальные,
без пользовательских названий/коллекций в удалённой телеметрии по умолчанию.

## Решения и открытые вопросы

- SAFE_DEFAULT: пять доменов в контракте, только проверенные домены в rollout.
- SAFE_DEFAULT: неизвестные/conflict всегда запрещают автоматическую запись/скрытие.
- DEFERRED: бюджет всего индекса после измерения, выбранное представление символов,
  конкретные границы сезонов для каждого источника, доменные лицензии.
- DEFERRED: Python для обучения выбирать с wheel support; системный Python 3.14
  не означает совместимость всего PyTorch/export toolchain.
- Нет вопросов, блокирующих загрузку публичных исследовательских ресурсов.
